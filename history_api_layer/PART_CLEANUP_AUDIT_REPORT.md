Проект: `MOEX_HISTORICAL_LAB_2Y/history_api_layer`
Режим: RESEARCH ONLY / READ ONLY / ADDITIVE ONLY / NO OVERWRITE / NO MASS DOWNLOAD / NO LIVE ORDERS.
Дата: 2026-11-22. Базовая линия: состояние после TIMEOUT HANDLING FIX
(SHA256 `fetch_archive_zip.py` = `9b304ddf33a1a3312657b4749818ff73a06c03bf65152a18d0752b77bb0ddb5b`,

## 1. Суть исправлений

### P1. Удаление `.part` предыдущего запуска (минимальное решение)

Причина: `cleanup_part_file()` удалял файл по фиксированному имени
`SBER_2025_uid.zip.part`, не подтверждая, что файл создан текущим запуском;
кроме того, `http_get_stream()` открывает временный файл в режиме `"wb"`
(усечение), то есть `.part` прошлого запуска был бы уничтожен уже при первой
записи.

Решение (архитектура загрузчика не изменена):
- в `run_fetch()` принадлежность определяется ДО первой сетевой попытки:
  `part_preexisting = tmp_path.exists()` по точному фиксированному пути;
- если `.part` существовал до запуска — он НЕ открывается (не усекается) и
  НЕ удаляется; факт фиксируется в мете (`part_preexisting: true`,
  `part_preexisting_note`), а тело текущего запуска пишется в УНИКАЛЬНОЕ
  имя `<имя>.part.<UTC-stamp>.<pid>[.<n>]` (с ротацией суффикса при занятых
  кандидатах);
- если `.part` до запуска не существовал (обычный случай) — используется
  прежнее фиксированное имя (обратная совместимость, прежние тесты зелёные).

### P2. Ранний возврат HTTP 404

Причина: ветка `if status == 404` выполняла `return meta` до общего
cleanup-блока — после последовательности timeout (частичный `.part`) -> 404
на втором эндпоинте временный файл текущего запуска оставался на диске.

Решение: цикл попыток обёрнут в `try/finally`; очистка выполняется в
`finally` при ЛЮБОМ неуспешном завершении: ранний возврат 404, неожиданный
200 в probe-режиме, тайм-аут, невозвратный статус, исчерпание 429-попыток
и даже непредвиденное исключение. Флаг `saved_ok=True` (устанавливается
только после успешного `tmp_path.replace(final_path)`) исключает cleanup
на успешном пути — прежняя семантика сохранена. Дублировавшие cleanup
вызовы (явный вызов в ветке NO_OVERWRITE-during-load и пост-цикловой
`if not executed`-блок) удалены как избыточные — единая точка очистки.

Дополнительно (defense-in-depth): `cleanup_part_file()` получила
предохранитель — имя обязано содержать `.part`, иначе удаление отвергается
с причиной `guard: имя не содержит .part`. Итоговый ZIP (`….zip`) и любые
посторонние имена через cleanup удалить невозможно в принципе.

## 2. Как определяется принадлежность `.part` текущему запуску

1. **Факт существования до первой попытки**: точечная проверка
   `tmp_path.exists()` по единственному фиксированному пути — до создания
   каталога попыток и до первого GET. Файл, существовавший в этот момент,
   заведомо создан не текущим запуском.
2. **Разделение путей**: при обнаружении предшественника текущий запуск
   переходит на уникальное имя `.part.<UTC-stamp>.<pid>[.<n>]` —
   пересечение с файлом предыдущего запуска исключено по построению.
3. **Единственный писатель своего пути**: удаляется ровно тот путь, в
   который текущий запуск писал тело (`http_get_stream(url, …, tmp_path, …)`).
   Никакого glob / очистки каталога.
4. **Предохранитель по имени**: `cleanup_part_file()` отказывается удалять
   имя без `.part` — итоговый ZIP недостижим для cleanup.
5. **Фиксация фактов в мете**: `part_preexisting`, `tmp_file`,
   `part_file_cleanup{path, removed, skipped_reason}` — проверяемо
   постфактум.

Гарантии: `.part` предыдущего запуска не удаляется и не усекается; итоговый
ZIP не удаляется и не перезаписывается (NO_OVERWRITE сохранён, включая
проверку «файл появился во время загрузки»); атомарная схема
tmp+`replace()` в том же каталоге сохранена; чужие файлы не затрагиваются.

## 5. Подтверждение отсутствия реальных GET

- Реальные HTTP-запросы не выполнялись: ни скрипт, ни тесты не обращались
  к сети. Все тесты идут через подменённый `urllib.request.urlopen`
  (перехватчик с планом реакций: тайм-ауты, 404, 429, синтетический 200);
  реальный `urlopen` никогда не вызывается.
- Сценарии «timeout» и «HTTP 404» воспроизводятся исключением
  `TimeoutError` / `urllib.error.HTTPError(404)` в моке; «успешный 200» —
  синтетическим ZIP-телом (`data/demo_fixtures`-совместимые синтетические
  свечи), без сетевого доступа.
- Единственная сетевая точка модуля — `urllib.request.urlopen` (статически
  проверяется тестом `test_no_real_http_clients_in_module`: в модуле нет
  requests/httpx/aiohttp/urllib3/голых сокетов).
- Токен в тестах — фиктивная строка тестового окружения
  (`dummy-token-for-test`); `hal_config.py` не изменялся.
