## 0. Резюме и ключевое ограничение

Создан новый изолированный каталог `history_api_layer/` с четырьмя самостоятельными скриптами и тестовым пакетом (**76 тестов, все проходят** — после раунда коррекции 1). Прототип соответствует рамке этапа 2А плана (раздел 12): **один логический read-only запрос на запуск** (физически — до 12 GET-попыток: 2 домена × до 6 попыток при 429, см. раздел 14.3), SBER, завершённый год 2025, 1M, годовой ZIP-архив; фиксирование структуры ZIP, фактического имени первого поля (UID vs FIGI), порядка полей, CRC и домена.

**Раунд коррекции 1 (аудит test-репозитория):** устранён блокирующий дефект P0 — параметры `instrument_id` и `year` теперь уходят серверу в URL запроса (`urllib.parse.urlencode`), проверено тестами на перехвате фактического `urllib.request.Request`; приведена структура (P1); исправлено правило пригодности 5M (P2); факт-учёт числа HTTP-вызовов (P3); полный прогон тестов 76/76 и SHA256 (P4). Детали — раздел 14.

**Критически важная фиксация (п. 7 задания):** реальный архив **не загружен**. В окружении песочницы переменная `TINKOFF_READONLY_TOKEN` **отсутствует** (fail-closed: скрипт не выполняет HTTP-запрос без токена), и TLS-соединение с обоими API-доменами из песочницы не устанавливается (перехват сертификата — свойство среды, не API). Проверки работоспособности выполнены **только на синтетическом фиксёре**, явно помеченном `synthetic`. Утверждения «прототип работает с реальными данными» **нет и не должно быть** — реальная проверка выполняется отдельным запуском на машине пользователя (см. раздел 11).

Факты окружения зафиксированы артефактами честно:
- `data/http_meta/fetch_meta_SBER_2025_20261122T093342Z.json` — `executed: false`, причина «токен отсутствует в окружении», HTTP-запросов `attempts: []`;
- `data/http_meta/fetch_meta_SBER_2025_20261122T093559Z.json` — контрольный GET без авторизации: обе попытки завершились сетевой ошибкой TLS (факт среды; HTTP-статус сервера не получен).

Оба артефакта созданы **до** раунда коррекции 1 (в `attempts[]` нет поля `url` с query-параметрами) и сохраняются как факт прогона до коррекции (NO OVERWRITE). После коррекции каждая попытка записывает полный `url` с `instrument_id` и `year`, плюс счётчики `http_requests_max_possible`/`http_requests_made` — это проверено тестами с перехватом urlopen (раздел 14.1).

## 5. Как устроен фактический ZIP

**Честный статус: фактический ZIP T-Invest History API не получен** (нет токена в окружении; TLS из песочницы не проходит — раздел 0). Ни одно свойство реального архива в этом отчёте не выдаётся за проверенный.

Что известно документированно (план 1.2, обе версии страницы метода, проверено 2026-11-22) и что именно фиксирует прототип при первом реальном запуске:

| Свойство | Документировано | Фиксируется прототипом (факт, не допущение) |
|---|---|---|
| Порядок полей | `UID, UTC, open, close, high, low, volume` (close раньше high/low) | Автодетект ролей колонок + эмпирическая сверка двух кандидатов порядка по OHLC-согласованности строк (`matches_documented_order`, rates обоих вариантов) |
| Метка времени | UTC, начало свечи | Автодетект формата (ISO/пробел/компакт/epoch), доля aware/наивных, выравнивание на :00, эмпирическая гипотеза TZ по границам сессий МСК |
| Объём | **в лотах** | Целостность, неотрицательность, распределение; эмпирическое подтверждение «лоты» — вне 2А (класс 3 сверки, план 10.2) |
| `is_complete` | **в документации нет** | Наличие/отсутствие колонки фиксируется фактом; прототип не требует её |
| Имя первого поля | **Расхождение версий: «UID» (портал) vs «FIGI» (зеркало)** | Автодетект вида значения (uuid ↔ figi-паттерн) и сверка с обоими идентификаторами конфига |
| Внутренняя структура ZIP | **Не документирована** | Члены ZIP, CRC (`testzip`), заголовок/разделитель/кодировка — фиксируются фактом |
| Домен | Два официальных (`tbank.ru`, `tinkoff.ru`) | Первый успешный GET фиксирует работающий; обе попытки пишутся в мету |
| HTTP 404 | Формулировка «нет данных за год» в повторной проверке документации не найдена (план 13.5) | Фиксируется фактом при появлении: статус-кандидат `absent_404` |

**Синтетический фиксёр** (`data/demo_fixtures/SBER_2025_SYNTHETIC.zip`, 3977 строк, 5 рабочих дней, документированный порядок полей, без заголовка, `%Y-%m-%dT%H:%M:%SZ`) — **не реальные данные**; он существует только для проверки работоспособности цепочки скриптов и тестов без сети и токена.

## 7. Какие проблемы данных найдены

**На синтетическом фиксёре (работоспособность детекторов, не реальные данные):** намеренно встроенные дефекты обнаруживаются корректно — точный дубликат и дубликат с конфликтом значений (`duplicate_ts_groups=2, conflicting=1`), строка с нарушением OHLC отбраковывается (`ohlc_validation`), метка вне года → FAILED, неполный последний день → последний 5M-бакет incomplete и исключён с учётом в B1/B2, минуты без сделок → `missing_within_span` с оговоркой плана 10.2.

**Изучением кода лаборатории (без изменений):**

1. **Проблема «runner.py записывал FIGI вместо тикера»: прямая проверка невозможна — `research/backtest/runner.py` в снимке ПУСТ (0 байт)** (так же пуст `research/instruments/registry.py` — план 3.1 подтверждён). Механизм, которым FIGI мог оказаться в поле тикера, подтверждается смежным кодом: (а) `build_session_top10.py:101` подставляет `instrument_uid` в поле `figi` при его отсутствии — идентификаторное смешение в кодовой базе реально; (б) research-вход строится по имени файла (`path.stem` = figi), а тикер разрешается **только** через реестр — при устаревшем/отсутствующем реестре любая выгрузка, печатающая «тикер», может вывести идентификатор файла; (в) TOP-10 существует в двух схемах (ключи uid и figi) в одном каталоге (план 3.7.6). Следствие для будущего адаптера: тикер берётся исключительно из реестра по UID, никогда из имён файлов — это уже учтено в `normalize_ids_fields.py` (проверка ID каждой строки против запрошенного инструмента).
2. **Известные недоработки, ограничивающие трактовку старых результатов** (план 3.7, без правок): `validate_row` пропускает NaN/inf; «заморозка» `is_complete=false` при повторных запусках; фиксированный `END_DATE=2026-11-14`; BOM-несовместимость загрузчиков с research; два пространства имён TOP-10. Прототип повторяет эти дефекты не намеренно и ничего из них не наследует.
3. **Окружение запуска**: 12-часовой прогон w01–w06 и его TOP-10 остаются неподтверждёнными; корректность контура не проверялась в рамках 2А (запрещено расширение объёма) — прототип не опирается на них ни в одном допущении.

### 14.3. P3 — учёт числа HTTP-вызовов (исправлено)

Сверка с отчётом: ранее заявлялось «один read-only GET», тогда как код допускал повторы. Фактическая семантика зафиксирована явно:
- один запуск = **один логический запрос** (один архив за год), физически — **до 12 GET-попыток** (`2 домена × MAX_HTTP_ATTEMPTS=6`); retry только при 429 (уважение Retry-After, потолок 60 с), бесконтрольного повторения нет — тест фиксирует ровно 12 попыток при постоянном 429 и остановку;
- 404 — без повторов и без перебора второго домена (тест: ровно 1 попытка);
- self-limit 20/мин сохранён (sliding window, мьютекс), помечен как СОБСТВЕННЫЙ лимит лаборатории, не лимит API;
- мета содержит точные счётчики `http_requests_max_possible`/`http_requests_made` (тест проверяет равенство 12 при исчерпании лимита повторов);
